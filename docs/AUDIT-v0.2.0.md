# НЕИГРЫ Android v0.2.0 — логический аудит

Дата аудита: 2026-09-24

## Итог

Версия v0.1.0 не была отправлена на реальное устройство как «готовая». Перед первой установкой проведён повторный аудит протокола, состояний и восстановления относительно установленного backend-патча и действующей веб-логики.

Итог автоматизированного логического прогона v0.2.0: **30 PASS / 0 FAIL**.

Это означает, что проверенные логические условия согласованы. Это **не** означает, что APK уже скомпилирован или проверен на конкретной модели Android TV: в текущем рабочем окружении нет Flutter SDK, поэтому `flutter analyze`, `flutter test` и реальная Android-сборка остаются обязанностью CI workflow.

## Исправлены 11 пунктов первого аудита

1. Добавлена синхронизация времени `sync_probe/sync_ack` на телефоне.
2. Добавлена синхронизация времени `sync_probe/sync_ack` на TV.
3. `done` сначала сохраняется локально и повторяется после reconnect с тем же `eventId`.
4. Pending `done` блокирует только тот запуск, к которому относится `runStartedAt`.
5. Старт финала блокируется до завершения отборочных обеими командами.
6. Добавлена `finish_season`.
7. Добавлена ручная коррекция timeout через `correct_timeout_to_success`.
8. Добавлены `show_summary` и `show_finale`.
9. Длинный текст `ГОТОВЬТЕСЬ` на телефоне масштабируется через `FittedBox`.
10. Controller/stage live keys и auth token сохраняются в Android secure storage и восстанавливаются после убийства процесса.
11. Pairing-код TV больше не зависит от локальных часов телевизора; обычные команды пульта блокируются offline, а `done` остаётся доступным для отложенной доставки.

## Дополнительные проблемы, найденные во втором проходе

### 1. Холодный запуск без интернета мог стереть живую сессию

Исправлено. Валидация сохранённого live key теперь различает:

- явный `404/403` — ключ недействителен, можно очистить;
- сетевую/временную ошибку — ключ сохраняется, клиент пытается восстановить соединение.

### 2. Протухшая live-сессия могла визуально оставаться ONLINE

Backend при завершении live не обязан немедленно закрывать уже существующий WebSocket. Поэтому и controller, и stage получили периодическую HTTPS-проверку live key. При `not_found/forbidden` клиент выходит из старой сессии.

### 3. Окончание видео могло потеряться при обрыве сети

Исправлено. TV хранит `instruction_ended` как pending-событие и повторяет его после reconnect, пока сервер не сменит фазу с `instruction`.

### 4. Финал без лимита времени показывался не как веб-версия

Исправлено. Для `headstart` и `sudden_death` после старта отображается прошедшее время `MM:SS.mmm`. Для `timed` остаётся обратный отсчёт.

### 5. Параллельные reconnect могли наслаиваться

`LiveSocket.connect()` теперь дедуплицирует одновременные попытки подключения, а WebSocket handshake ограничен таймаутом 12 секунд.

### 6. Offline cold-start мог ошибочно стереть auth token

Исправлено. Токен удаляется только при явном `401/unauthorized`; сетевой сбой не превращается в logout.

### 7. Плавающие версии Flutter-зависимостей создавали риск сломать CI без изменения кода

Исправлено. Зависимости в `pubspec.yaml` закреплены точными версиями. Workflow закреплён на Flutter `3.44.9`.

## Проверенные тайминги

Клиент и установленный server.js совпадают по критическим константам:

- подготовка обычного испытания: `12000 ms`;
- длительность обычного/timed испытания: `60000 ms`;
- подготовка финала: `8000 ms`;
- серверное окно поздней доставки `done`: `30000 ms`;
- клиент перестаёт повторять слишком старое `done` после `32000 ms`.

Проверены также точки отображения `3 → 2 → 1` и клиентская защита слишком раннего нажатия второй команды при headstart.

## Что ещё нельзя доказать без настоящей Android-сборки/устройства

1. Что Flutter/Gradle компилятор не найдёт типовую/плагинную ошибку, которую невозможно выявить без Flutter SDK.
2. Реальное декодирование конкретных mp4/wav/mp3 на конкретном телевизоре.
3. Поведение D-pad/фокуса на конкретной прошивке Android TV.
4. Реальные системные ограничения фоновой работы/энергосбережения конкретного телефона.
5. Реальный размер/читабельность UI на разных DPI и overscan телевизоров.

После этого аудита первая GitHub-сборка уже имеет смысл как **компиляционный тест**, а первая установка — как **device/media/UI тест**, а не как поиск очевидных логических дыр.
